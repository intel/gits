# Studio modules

Studio modules are Windows x64 DLLs that `gitsStudio` loads at runtime and shows in its sidebar.
A module is built from the same source tree, with the same toolchain and build configuration, as
the Studio it runs in, and is deployed together with it. Nothing checks compatibility between
independently built Studio and module binaries, and none is provided.

The tree contains two modules:

| Module | Folder | Purpose |
|--------|--------|---------|
| RTSR | `rtsr/` | Real-time shader replacement. The production module. |
| Hello | `hello_module/` | The smallest possible module, as a starting point. The build-tree Studio runs with it, but it is not installed. |

`module-contract.yaml` summarizes the same contract in a structured form.

## Deployment layout

Each module lives in its own folder under `Modules/`:

```text
<Studio directory>/
  gitsStudio.exe
  Modules/
    <id>/
      module.dll
      module.pdb          # optional
      <dependency>.dll    # optional: DLLs the module imports
```

Studio looks for `Modules/` next to `gitsStudio.exe`. When that folder does not exist, it uses
`Modules/` in the GITS installation (the GITS base path). It loads `module.dll` from every direct
subfolder. A module that cannot be loaded is logged and skipped.

A Studio run from the build tree has its own `Modules/`: every module built in the tree is copied
next to it (see [Building a module](#building-a-module)), so it runs with all of them.

The DLLs a module imports are looked up next to `module.dll`, next to `gitsStudio.exe`, and in
System32.

Studio never unloads a module: the DLL stays loaded until Studio exits. Replacing `module.dll`
therefore needs a Studio restart, and the file is locked while Studio runs.

## The module export

A module DLL exports one function. It is generated by `GITS_GUI_REGISTER_MODULE`, declared in
`common/include/moduleRegistry.h`:

```cpp
GITS_GUI_REGISTER_MODULE("hello", ::gits::gui::HelloPanel, "Hello", "Minimal Studio module")
```

The macro defines:

```cpp
extern "C" __declspec(dllexport) void GitsGuiModule(const ModuleContext* context,
                                                    ModuleRegistration* registration);
```

Studio calls `GitsGuiModule` right after loading the DLL. The function binds the module to Studio
(see [What a module shares with Studio](#what-a-module-shares-with-studio)) and returns the
module's registration: its id, a factory that creates its root panel, and the name and hint
shown on its sidebar button.

The first argument is the module's id. Studio identifies a module by it, the way GITS identifies
a plugin by the name it reports. The id must be unique among modules, ignoring case; by
convention it is lowercase and equals the name of the module's folder under `Modules/`. Studio
logs and skips a module whose id is empty or already taken. The id is separate from the sidebar
label, so `"hello"` can be shown as "Hello".

Use the macro exactly once per module, in one source file, at global scope.

## Root panel

A module's UI is a single root panel deriving from `ModuleBasePanel`
(`common/include/moduleBasePanel.h`). It must be default-constructible and implement:

- `GetName()`: the sidebar label.
- `GetNameHint()`: the sidebar tooltip.
- `Render()`: draws the module's UI with ImGui.
- `Activate()`, `Deactivate()` and `IsActive()`: start and stop the module's work. Studio calls
  them when the user checks or unchecks the module's sidebar button.
- `Plugins(Api)`, optional: names of GITS plugins Studio adds to every run it launches while the
  module is active.

`GetName()` and `GetNameHint()` return `const char*`, for example a `constexpr` constant, and
`Plugins()` returns a reference to a list the module keeps, for example a function-local
`static const std::vector<std::string>`. A `std::string` or `std::vector` returned by value
would be freed by Studio (see [Memory](#memory)).

Studio creates the panel once and destroys it at shutdown. The destructor must stop whatever
`Activate()` started.

## What a module shares with Studio

Studio and every module DLL contain their own copy of the C++ runtime and of the libraries they
link. The few things they must share are bound by `GitsGuiModule` before the panel is created.
Studio passes them in a `ModuleContext`, and `BindModule` installs them in the module
(`common/include/moduleContext.h` and `common/moduleContext.cpp`):

| Shared with Studio | What the module sees |
|--------------------|----------------------|
| ImGui context and allocator | Plain ImGui calls draw into Studio's UI. |
| Log | `LOG_INFO`, `LOG_ERROR` and so on go to Studio's log, filtered by Studio's level. |
| EventBus | `EventBus::GetInstance()` returns Studio's bus, from any thread. |
| BaseContext | `BaseContext::GetBaseInstance()` returns Studio's context: selected action, paths, GITS player path. |

Everything else exists once per binary and is not shared:

- other Studio singletons, for example `StudioContext::GetInstance()`;
- ImGui helper state, for example `ImGuiHelper::CurrentUIScale()` and the fonts;
- the heap of the C and C++ runtime (see [Memory](#memory)).

A module that needs more of Studio requires a change to `ModuleContext` and `BindModule`.

## Memory

Studio and each module DLL have their own heap, and memory must be freed by the binary that
allocated it. In Debug builds, a block freed by the other binary stops Studio with a heap
assertion; in Release builds, it can corrupt the heap. This takes no effort in practice:

- Inside the module, use `std::string`, containers and the rest of the standard library as usual.
- Do not hand Studio anything it would have to free or resize: no `std::string`, `std::vector` or
  other owning object by value, and no memory from `malloc`. `ModuleBasePanel` is shaped for this:
  names are `const char*` and the plugin list is returned by reference.
- Read the BaseContext, but do not change it.
- Subscribe and publish on the EventBus freely. Studio's bus stores handlers and events with its
  own code, and each event and handler is destroyed by the code that created it.

## Rules for module code

ImGui:
- Studio owns the ImGui context. A module must not create or destroy a context, or change ImGui's
  allocator or fonts.
- Call ImGui only from `Render()`. It runs on Studio's UI thread, inside the content area Studio
  provides, so the module does not open its own window.

Events and Studio state:
- Use the EventBus as Studio code does and read the BaseContext, but not from static
  initializers: those run when the DLL is loaded, before `GitsGuiModule` binds the module.
- Subscribe on the EventBus once, for the panel's whole life. `EventBus::unsubscribe` cannot
  remove a lambda, and the panel lives until Studio shuts down.

Threads:
- Worker threads are fine and may publish on the EventBus. Only the UI thread may call ImGui.
  Stop threads, servers and sockets in `Deactivate()` and in the destructor.

Errors:
- Studio catches exceptions thrown from the factory, `Activate()`, `Deactivate()` and
  `Plugins()`, and logs them. A panel that cannot be created is dropped from the sidebar; a failed
  `Activate()` leaves the button unchecked. `Render()` is not guarded, like any Studio panel.

## Loading and shutdown

1. Studio initializes its log, configuration, contexts, EventBus and ImGui context.
2. When Studio builds its content panel, `ModuleRegistry::CreateModules()` finds `Modules/` and
   loads every `module.dll`, which constructs the DLL's static objects.
3. Studio calls `GitsGuiModule`. The module binds to Studio and returns its registration, and
   Studio adds the module's button to the sidebar, unless another module already uses its id.
4. Studio creates every registered panel. If exactly one module is loaded, Studio activates it.
5. The sidebar button activates and deactivates the module; selecting it shows its `Render()`.
6. At shutdown, Studio destroys the panels.
7. The DLLs stay loaded until the process exits.

## Building a module

1. Create `gui_apps/modules/<name>/` with the root panel and one `GITS_GUI_REGISTER_MODULE` line
   whose first argument is the module's id, for example `"mymodule"`. `hello_module/` is the
   template.
2. Add a `CMakeLists.txt`:

   ```cmake
   add_library(my_module SHARED
     ${CMAKE_CURRENT_SOURCE_DIR}/myPanel.h
     ${CMAKE_CURRENT_SOURCE_DIR}/myPanel.cpp
   )
   target_link_libraries(my_module
   PRIVATE
     module_common
     gui_common
     common_interface
     imgui_common
     log
     configuration
     stream
   )
   add_dependencies(my_module config_codegen)
   set_target_properties(my_module PROPERTIES FOLDER "${GUI_MODULES_FOLDER}")
   gui_module(my_module mymodule)
   gui_module_install(my_module)
   ```

   - `gui_module(target id)` makes the target a Windows x64 DLL named `module.dll` that belongs
     in `Modules/<id>/`; pass the module's id. It links `imgui_addons`, the ImGui add-ons that
     Studio compiles into its executable. Every time the module is built, its `module.dll` is
     copied into `Modules/<id>/` next to the build-tree Studio.
   - `gui_module_install(target)` installs `module.dll` and its PDB into `Modules/<id>/`, as part of
     the `gits_studio` component. Leave it out for a module that is not shipped, as `hello_module`
     does.
3. Add the folder to `gui_apps/modules/CMakeLists.txt`, inside the `if(WIN64)` block.

## Running and debugging

Building `gits_studio` builds every module in the tree, and each one is copied next to the
build-tree `gitsStudio.exe`, so running or debugging that executable runs Studio with all modules,
`hello_module` included. Studio activates a module at startup only when exactly one is loaded;
with more, activate them from the sidebar.

The copies always match Studio's configuration. A Studio that falls back to the modules of the
GITS installation must come from the same configuration as that installation: the C++ object
layouts differ between Debug and Release builds.

## Troubleshooting

Studio writes its log to the in-app log view and to the debugger output.

| Log line or symptom | Cause |
|---------------------|-------|
| `ModuleRegistry: No Modules directory found` | Neither `Modules/` next to Studio nor `Modules/` in the GITS installation exists. |
| `ModuleRegistry: Loading <path> failed with Windows error 126` | A DLL the module imports was not found next to `module.dll`, next to Studio, or in System32. |
| `ModuleRegistry: <path> does not export GitsGuiModule` | `GITS_GUI_REGISTER_MODULE` is missing, or is in a file that is not compiled. |
| `ModuleRegistry: <path> has no module id` | The first argument of `GITS_GUI_REGISTER_MODULE` is empty. |
| `ModuleRegistry: <path> uses the module id <id> of another module` | Two modules declare the same id, ignoring case, or one module is installed twice under different folders. |
| `ModuleRegistry: Registering`, `Creating` or `Activating ... failed` | The module's code threw; the message follows. |
| Crash or nonsense state right after loading | Studio and the module come from different builds or configurations. |
| Debug heap assertion such as `_CrtIsValidHeapPointer`, or heap corruption in Release | One binary freed memory the other allocated: the module handed Studio an owning object or changed Studio's state (see [Memory](#memory)). |
| Events never arrive, or the BaseContext shows defaults | The EventBus or BaseContext was used from a static initializer. |
