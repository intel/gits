# Overview 

**GITS Studio** supports **modules** that extend the functionality of the **GITS Studio**. A **GITS Module** provides a user interface and can be used to show data, analysis or other information to the user. **GITS Modules** can integrate with **GITS Plugins** and allow the user to interact with the API stream captured through the interposer.

Currently  **GITS Modules** are Windows x64 DLLs that **GITS Studio** loads at runtime. A module is built from the same source tree, with the same toolchain and build configuration, as the **GITS Studio** it runs in, and is deployed together with it. Nothing checks compatibility between independently built **GITS Studio** and module binaries, and none is provided.

# Deployment

Each **GITS Module** lives in its own folder under `Modules/`:

--8<-- "modules_folder.md"

**GITS Studio** looks for `Modules/` next to `gitsStudio.exe`. When that folder does not exist, it uses `Modules/` in the GITS installation (the GITS base path). It loads `module.dll` from every direct subfolder. A **GITS Module** that cannot be loaded is logged and skipped.

A **GITS Studio** run from the build tree has its own `Modules/`: every **GITS Module** built in the tree is copied next to it (see [Building a **GITS Module**](#building-a-module)), so it runs with all of them.

**GITS Studio** never unloads a **GITS Module**: the DLL stays loaded until it exits. Replacing `module.dll` therefore needs a **GITS Studio** restart, and the file is locked while it runs.

# Development

## Module Registration

A **GITS Module** DLL exports one function. It is generated by `GITS_GUI_REGISTER_MODULE`, declared in `common/include/moduleRegistry.h`, which takes the **GITS Module**'s ID and the type of its root panel, which must implement the class `ModuleBasePanel` (`common/include/moduleBasePanel.h`):

```cpp
GITS_GUI_REGISTER_MODULE("hello", ::gits::gui::HelloPanel)
```

The macro defines:

```cpp
extern "C" __declspec(dllexport) void GitsGuiModule(const ModuleContext* context,
                                                    ModuleRegistration* registration);
```

Every **GITS Module** must have a unique module ID, ignoring case. **GITS Studio** identifies a **GITS Module** by it, similar to the way GITS identifies a **GITS Plugin** by the name it reports. By convention it is lowercase and equals the name of the module's folder under `Modules/`. **GITS Studio** logs and skips a module whose ID is empty or already taken, without building its panel.

Use the macro exactly once per module, in one source file, at global scope.

## Module Root Panel

A **GITS Module**'s UI is a single root panel deriving from `ModuleBasePanel` (`common/include/moduleBasePanel.h`) and uses ImGui to render it's content. It must be default-constructible and implement:

- `GetName()`: the (brief) name of the module.
- `GetNameHint()`: the (short) description of the module.
- `Render()`: draws the module's UI.
- `OnActivate()` and `OnDeactivate()`, optional hooks: start and stop the module's work. `OnActivate()` returns `false` when the module cannot start. Studio calls the base class's `Activate()` and `Deactivate()` to activate or deactivate the module; they call the hooks.
- `Plugins(Api)`, optional: names of **GITS Plugins** the module requires to be loaded by **GITS Studio* while the module is active.

`GetName()` and `GetNameHint()` return `const char*`, for example a `constexpr` constant, and `Plugins()` returns a reference to a list the module keeps, for example a function-local `static const std::vector<std::string>`.

The base class owns the active state. `IsActive()` is true from a successful `OnActivate()` until `Deactivate()`. Activating an active module or deactivating an inactive one does nothing.

**GITS Studio** creates the panel once and destroys it at shutdown. The destructor must stop whatever `OnActivate()` started.

## What a module shares with GITS Studio

**GITS Studio** and every module DLL contain their own copy of the C++ runtime and of the libraries they link. The few things they must share are bound by `GitsGuiModule` before the panel is created. **GITS Studio** passes them in a `ModuleContext`, and `BindModule` installs them in the module (`common/include/moduleContext.h` and `common/moduleContext.cpp`):

| Shared with **GITS Studio** | What the module sees |
|--------------------|----------------------|
| ImGui context and allocator | Plain ImGui calls draw into Studio's UI. |
| Log | `LOG_INFO`, `LOG_ERROR` and so on go to Studio's log, filtered by Studio's level. |
| EventBus | `EventBus::GetInstance()` returns Studio's bus, from any thread. |
| BaseContext | `BaseContext::GetBaseInstance()` returns Studio's context: selected action, paths, GITS player path. |

Everything else exists once per binary and is not shared:

- other **GITS Studio** singletons, for example `StudioContext::GetInstance()`;
- ImGui helper state, for example `ImGuiHelper::CurrentUIScale()` and the fonts;
- the heap of the C and C++ runtime (see [Memory](#memory)).

A module that needs more of **GITS Studio** requires a change to `ModuleContext` and `BindModule`.

## Memory

**GITS Studio** and each module DLL have their own heap, and memory must be freed by the binary that allocated it. In Debug builds, a block freed by the other binary stops **GITS Studio** with a heap assertion; in Release builds, it can corrupt the heap. This takes no effort in practice:

- Do not hand **GITS Studio** anything it would have to free or resize: no `std::string`, `std::vector` or other owning object by value, and no memory from `malloc`. `ModuleBasePanel` is shaped for this: names are `const char*` and the plugin list is returned by reference.
- Read the `BaseContext`, but do not change it.
- Subscribe and publish on the `EventBus` freely. **GITS Studio**'s bus stores handlers and events with its
  own code, and each event and handler is destroyed by the code that created it.

## Rules for module code

ImGui:

- **GITS Studio** owns the ImGui context. A **GITS Module** must not create or destroy a context, or change ImGui's allocator or fonts.
- Call ImGui only from `Render()`. It runs on **GITS Studio**'s UI thread, inside the content area **GITS Studio** provides, so the **GITS Module** does not open its own window.

Events and **GITS Studio** state:

- Use the `EventBus` as **GITS Studio** code does and read the `BaseContext`, but not from static initializers: those run when the DLL is loaded, before `GitsGuiModule` binds the module.
- Subscribe on the `EventBus` once, for the panel's whole life. `EventBus::unsubscribe` cannot remove a lambda, and the panel lives until **GITS Studio** shuts down.

Threads:

- Worker threads are fine and may publish on the `EventBus`. Only the UI thread may call ImGui. Stop threads, servers and sockets in `Deactivate()` and in the destructor.

Errors:

- **GITS Studio** catches exceptions thrown from the panel's constructor, `OnActivate()`, `OnDeactivate()` and `Plugins()`, and logs them. A panel that cannot be created is dropped from the module list; a failed `OnActivate()` leaves the button unchecked. `Render()` is not guarded, like any **GITS Studio** panel.

## Lifecycle: loading and shutdown

1. **GITS Studio** initializes its log, configuration, contexts, `EventBus` and ImGui context.
2. When **GITS Studio** builds its content panel, `ModuleRegistry::CreateModules()` finds `Modules/` and loads every `module.dll`, which constructs the DLL's static objects.
3. **GITS Studio** calls `GitsGuiModule`. The **GITS Module** binds to **GITS Studio** and returns its registration, and **GITS Studio** is free to use the **GITS Module**, unless the ID is already in use.
4. If exactly one **GITS Module** is loaded, **GITS Studio** activates it.
5. If the **GITS Module** is activated it's `Render()` method.
6. At shutdown, **GITS Studio** destroys the panels.
7. The DLLs stay loaded until the process exits.

## Building a GITS Module

1. Create `gui_apps/modules/<name>/` with the root panel and one `GITS_GUI_REGISTER_MODULE` line, whose first argument is the module's id, for example `"mymodule"`. `hello_module/` is the template.
2. Add a `CMakeLists.txt`. Name the folder after the module's id, as GITS plugin folders are named after the plugin (`Modules/rtsr/`, like `Plugins/DirectX/rtsr/`).

   ```cmake
   if(WIN64)
     add_library(my_module SHARED
       ${CMAKE_CURRENT_SOURCE_DIR}/myPanel.h
       ${CMAKE_CURRENT_SOURCE_DIR}/myPanel.cpp
     )
     gui_module(my_module mymodule INSTALL)
   endif()
   ```

  `gui_module(target folder [INSTALL])` makes the target a Windows x64 DLL named `module.dll` that belongs in `Modules/<folder>/`; pass the module's id. It links the libraries every module needs (`module_common`, `gui_common`, `log`, `stream` and the others) and the ImGui add-ons that **GITS Studio** compiles into its executable, depends on `config_codegen`, and sets the IDE folder. Add the module's own libraries with `target_link_libraries`. Every time the module is built, its `module.dll` is copied into `Modules/<folder>/` next to the build-tree **GITS Studio**. With `INSTALL`, `module.dll` and its PDB are also installed into `Modules/<folder>/`, as part of the `gits_studio` component. Leave `INSTALL` out for a module that is not shipped, as `hello_module` does.

3. Add `add_subdirectory(<name>)` to `gui_apps/modules/CMakeLists.txt`. Guard the target with
   `if(WIN64)` inside the module's own folder, as `hello_module` and `rtsr` do.

## Running and debugging

Building the project/target `gits_studio` builds every **GITS Module** in the tree, and each one is copied next to the build-tree `gitsStudio.exe`, so running or debugging that executable runs **GITS Studio** with all modules, `hello_module` included. **GITS Studio** activates a module at startup only when exactly one is loaded,  otherwise they have to be activated manually.

The copies always match **GITS Studio**'s configuration. A **GITS Studio** that falls back to the **GITS Module**s of the GITS installation must come from the same configuration as that installation: the C++ object layouts differ between Debug and Release builds.

## Troubleshooting

**GITS Studio** writes its log to the in-app log view and to the debugger output.

| Log line or symptom | Cause |
|---------------------|-----    --|
| `ModuleRegistry: No Modules directory found` | Neither `Modules/` next to **GITS Studio** nor `Modules/` in the GITS installation exists. |
| `ModuleRegistry: Loading <path> failed with Windows error 126` | A DLL the module imports was not found next to `module.dll`, next to **GITS Studio**, or in System32. |
| `ModuleRegistry: <path> does not export GitsGuiModule` | `GITS_GUI_REGISTER_MODULE` is missing, or is in a file that is not compiled. |
| `ModuleRegistry: <path> has no module id` | The first argument of `GITS_GUI_REGISTER_MODULE` is empty. |
| `ModuleRegistry: <path> uses the module id <id> of another module` | Two modules declare the same id, ignoring case, or one module is installed twice under different folders. |
| `ModuleRegistry: Creating` or `Activating ... failed` | The module's code threw; the message follows. |
| Crash or nonsense state right after loading | **GITS Studio** and the module come from different builds or configurations. |
| Debug heap assertion such as `_CrtIsValidHeapPointer`, or heap corruption in Release | One binary freed memory the other allocated: the module handed **GITS Studio** an owning object or changed **GITS Studio**'s state (see [Memory](#memory)). |
| Events never arrive, or the BaseContext shows defaults | The EventBus or BaseContext was used from a static initializer. |
